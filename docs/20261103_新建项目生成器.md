# 新建项目生成器（以本工程为基调）

日期：2026-11-03
入口：侧栏「工作台 → 新建项目」（`internal/view/page_newproject.go`）
引擎：`internal/scaffold`

## 一、这个功能解决什么

每次要开一个新桌面端工程，都要把 bestuav-mygo 复制一遍、改 module 名（import 里近百处）、
改品牌常量、删掉一堆演示菜单、重新生成更新密钥、改 CI……一轮下来半小时，还容易漏。
这个功能把这一整套做成向导：填 5 个字段、勾几个菜单分组，等一两分钟拿一个**能编译、
能发版、能自动更新**的工程。

## 二、生成流程（9 步）

| # | 步骤 | 做什么 |
| --- | --- | --- |
| 1 | 检查模板来源 | 优先本地源码目录，缺失时用 exe 内置快照 |
| 2 | 复制工程骨架 | 白名单复制（见下），丢掉本项目的 docs 与截图；选了图标就替换 `resources/icon.png` |
| 3 | 重写模块路径 | `bestuav-mygo/...` → `<新项目>/...`，含 `go.mod` 的 module 行 |
| 4 | 生成更新密钥 | `go tool mygo keygen -o <用户配置目录>/mygo/update-keys/<项目>` |
| 5 | 改写产品标识 | `appmeta.go` 三个常量、`mygo.json` 五个字段、脚本里的项目名 |
| 6 | 裁剪菜单注册表 | AST 按分组名过滤，同时摘掉生成器自己的菜单项 |
| 7 | 删除页面文件 | 逐个删 + 每次编译该包，编不过就写回（见「已知取舍」） |
| 8 | 生成文档 + git | README / CHANGELOG / `docs/首次发布.md`；`git init` + `origin`（**不 push**） |
| 9 | 编译自检 | `go build ./...`，失败直接报错，不交付坏工程 |

## 三、几个关键决策（为什么这么做）

### 1. 模板来源：本地源码优先 + 内置快照兜底

- 本地源码（`go run` 时自动识别当前目录）：永远与最新代码同步，开发期最实用。
- 内置快照 `internal/scaffold/testdata/template`：打包后的 exe 里没有源码，靠它兜底。
- 放 `testdata/` 是刻意的：go 工具链忽略该目录，快照里的 `.go` 不会被重复编译；
  而 `go:embed all:...` 仍能读到。快照里的 `go.mod`/`go.sum` 改名成 `.snapshot`
  存放——**`go:embed` 拒绝嵌入含 `go.mod` 的目录**（会当成另一个 module）。

刷新快照：

```bash
python scripts/snapshot-template.py          # 刷新
python scripts/snapshot-template.py --check  # 校验是否与源码一致（发版前跑）
```

⚠️ 白名单在 `scripts/snapshot-template.py` 与 `internal/scaffold/template.go` 各有一份，
改一边必须同步另一边。

### 2. 白名单复制，不是整仓复制

带走：`internal/`、`scripts/`、`resources/`、`.github/`、`.agents/`、`go.mod`、`go.sum`、
`mygo.json`、`main.go`、`.gitignore`。
不带：`docs/`（本项目历史笔记）、`README/CHANGELOG/RELEASING`（新项目重新生成）、
`internal/scaffold`（生成器自身）、`internal/view/page_newproject.go`（依赖生成器）。

### 3. 用 AST 裁剪注册表，不用正则

`registry.go` 里每个分组是多行复合字面量。这里用 `go/parser` 拿到每个元素的精确字节
区间，**按位置删除整行**，保留的分组原文一字不动。裁剪后还会：

- `format.Source` 保证语法合法；
- 断言每个「应保留」的分组标题仍在文件里（防误删别组）；
- 清理因裁剪而变空的 import（例如首页组的 `onEnter` 用过 `time.Time`，该组被删后
  `time` 就没人用了，Go 会直接报 `imported and not used`）。

### 4. 删页面文件：逐个删 + 编译验证 + 失败写回

页面文件之间不是彼此独立的，实测踩到两个坑：

- `page_home.go` 里的 `greeting()` 被首页欢迎页调用 → 函数判定「可删」，整份文件不能删；
- `page_demo_features.go` 定义的一批类型被 `App` 结构体字段引用 → 删掉当场编不过。

所以这里**一次只删一个文件、删完立刻 `go build ./internal/view/`**，编不过就原样写回。
代价是每个候选文件一次编译（约 1 秒），换来的是不可能交付一个编不过的工程。

### 5. 密钥放项目外，按项目分目录

私钥写到 `<用户配置目录>/mygo/update-keys/<项目名>/mygo-update.key`，公钥自动写进
`mygo.json` 的 `updates.publicKey`。

**必须分目录**：若两个项目共用默认的同一个 key 文件，后生成的项目会覆盖前一个的私钥；
私钥一换，前一个项目已安装的客户端再也验不过新包（公钥固化在旧客户端里），不可逆。

生成完成后向导会把私钥**显示一次**并提供「复制私钥」，操作路径写在生成的
`docs/首次发布.md` 里：GitHub 仓库 → Settings → Secrets → `MYGO_UPDATER_PRIVATE_KEY`。

### 6. git 只 init + 配 remote，不 push

仓库是否已存在、本机凭据是否可用都不由生成器决定。最后一步失败会把「明明成功了的」
步骤标红。所以只配好远程，推送命令给用户自己执行。

## 四、已知取舍与限制

1. **部分页面文件会被保留**：仍被 `App` 结构体或其它页面引用的演示文件（如
   `page_demo_features.go`、`page_home.go`）删不掉——要彻底删得同时剥掉 `App` 的字段
   与初始化代码，风险远大于收益。向导会显示「保留 N 个（仍被其它代码引用）」，用户在
   新项目里可以慢慢清。

   **文件数实测**：复制 101 个 → 裁剪后 86 个（视勾选分组而定）。剩下的构成：
   `internal/view` 顶层约 25 个（`App`/`registry`/业务页）、`internal/view/{blackhole,
   effort,piano,fx}` 15 个、`internal/ui` 15 个（canvas/anim/kit/icons 这套自绘工具链）、
   其余为 store/logging/settings 等基础设施。要再砍到 60 出头，必须拆 `App` 结构体与
   那三个演示包的耦合（`bh`/`es`/`pi` 字段及其初始化），属于独立一轮的改造。
2. **`internal/view/*_test.go` 会被删除**：这些测试断言的是演示菜单内容，任意裁剪分组
   都会让它们失败。其它包（kit / canvas / settings / store）的测试全部保留。
3. **依赖本机 Go 工具链**：密钥生成与编译自检都要 `go` 命令，纯使用者机器上会明确报错。
4. **快照会过期**：改了源码不刷新快照，exe 兜底路径会用旧模板。发版前跑
   `--check`。

## 五、验证方式

```bash
go test ./internal/scaffold/ -count=1                 # 含 45 秒端到端（生成 + 编译自检）
go test ./internal/scaffold/ -count=1 -short          # 跳过端到端
go test ./internal/view/ -count=1 -run TestNewProject # 向导页渲染
```

端到端测试会：从当前源码生成一个项目（保留「工作台」分组）→ 断言 `page_task.go` 还在、
`page_piano.go` 已删 → 跑 `go build ./...` 必须通过。

## 六、本机手工试跑

```bash
go run .         # 打开应用 → 工作台 → 新建项目
```

模板来源会自动识别当前目录。目标目录留空时默认取「当前目录的上级/项目名」。
