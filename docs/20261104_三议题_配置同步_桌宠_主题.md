## 一、配置与数据同步

### 1.1 现在有哪些东西需要跟着人走

| 数据 | 位置 | 是否适合跨设备 |
|---|---|---|
| 偏好 `settings.json` | 配置目录（Windows `%APPDATA%`，macOS `Application Support`，Linux `~/.config`） | 大部分可以；少数是**设备相关**（见 1.3） |
| 业务数据 `data.db`（SQLite：task / license_record / app_event / page_pref / schema_meta） | 本机数据目录（Windows `%LOCALAPPDATA%`，Linux `~/.local/share`） | 可以，但要处理版本与合并 |
| 页面私有状态 `page_pref` | 在 `data.db` 里 | 可以（筛选条件、草稿） |
| 背景图片 | 用户选择的绝对路径 | 路径不可跨平台，必须内嵌或清空 |
| 日志 `logs/` | 数据目录 | 不需要同步（排障用，体积大） |
| 窗口位置/大小 | mygo 窗口状态 | 不需要（跟屏幕布局走） |
| 授权凭证、快捷键 | 在库 / settings 里 | 需要（业务数据） |

关键差异：**配置是小 JSON，数据是 SQLite**，背景图是外部文件——三者不能用同一种方式搬。

### 1.2 四个候选方案

| 方案 | 用户操作 | 开发量 | 运维 | 冲突处理 | 适用 |
|---|---|---|---|---|---|
| **A. 导出 / 导入文件** | 在旧机导出、新机导入 | 小（约 600–800 行 + 测试） | 无 | 覆盖 + 自动备份；可加「合并」 | 首次落地、换机、备份 |
| B. 直连第三方云（WebDAV / 网盘 API / S3） | 配一次账号 | 中（OAuth、各平台 SDK、密钥保管） | 无自建服务，但依赖第三方 | 需自己做 | 不想装云盘客户端时 |
| **C. 自建同步服务** | 注册账号 / 配对设备 | 大（服务端 + 客户端 + 冲突 + 安全 + 运维） | 有（服务器、备份、升级、隐私） | 服务端可做细 | 多用户、长期产品化 |
| **D. 同步文件夹**（用户已有的 OneDrive / iCloud / 坚果云 / Dropbox 目录） | 选一个已同步的目录 | 小到中（A 的 40%） | 无 | 云盘可能产生 conflicted copy；用 mtime + 设备 id 提示 | 3 台机器、低频同步 |

**推荐路线：A → D →（真需要多用户时再）C。**
理由：A 不需要任何服务端与网络，风险和隐私最小，能立刻解决「换机不用重配」；
D 复用用户已有的云盘客户端，几乎零运维；C 的成本主要不在代码，而在长期运维与安全，
现在做属于过度设计。

### 1.3 A 方案设计（导出 / 导入包）

**包格式**（zip，扩展名 `.mygo-profile.zip`）：

```
manifest.json          格式版本 / 应用标识 / 应用版本 / schemaVersion / 设备名 / 平台 / 导出时间 / 内容清单
settings.json          只含可移植字段（见下表）
data.db                VACUUM INTO 的一致性快照（可选：不导出业务数据时省略）
background.<ext>       背景图（可选；导入时复制到本机数据目录并改写路径）
README.txt             说明「包含什么、不含什么、如何恢复」
```

`manifest.json` 示例：

```json
{
  "format": 1,
  "app": "com.bestuav.quantum",
  "appVersion": "0.1.9",
  "schemaVersion": "2",
  "device": "DESKTOP-ABC",
  "platform": "windows/amd64",
  "exportedAt": "2026-11-04T12:00:00+08:00",
  "includes": ["settings", "data", "background"]
}
```

**哪些字段导入、哪些忽略**（关键设计）：

| 字段 | 处理 |
|---|---|
| theme / palette / fontSize / closeMode / shortcuts / menuOpacity / contentOpacity / pageIdleMinutes / sidebarCollapsed | 导入 |
| backgroundImage | 包内有图 → 复制到本机数据目录并改写路径；包内无图 → 清空（避免跨平台死路径） |
| openAtLogin（开机自启） | **不导入**：每台机器的登录项要用户自己确认（导入时可提示） |
| allowMultiInstance（多开） | 不导入（或保留本机） |
| ignoredVersion | 不导入 |
| 窗口位置/大小、日志 | 不导入、不导出 |

**导入流程**（设置 → 关于与诊断 → 数据与诊断）：

1. 选择文件 → 校验 `app` 标识一致、`format` 支持、`schemaVersion` **不高于**当前（低版本可迁移，高版本拒绝并提示先升级）；
2. 预览：将覆盖哪些内容、当前数据会备份到哪（`settings.json.bak-<时间>`、`data.db.bak-<时间>`）；
3. 备份 → 写入 → 提示「重启后生效」→ `mygo.App.Relaunch()`。

**导出流程**：同一入口「导出配置与数据…」，两个选项：
「只导出设置（不含任务/授权）」/「导出设置 + 数据」；导出前提示 zip 含授权凭证。

**安全**：不联网、不上传；zip 内含凭证属于敏感数据，导出时明确提示。
后续可选「密码加密导出」（AES-GCM + 用户口令），默认关闭。

**CLI**（给三台机器批量/首次配置用）：

```bash
量子科学.exe --export-profile=D:\backup\me.mygo-profile.zip
量子科学.exe --import-profile=D:\backup\me.mygo-profile.zip   # 启动前导入，完成后正常启动
```

导入在取单实例锁之后、`NewApp` 之前执行；导出在应用就绪后执行并退出。

**兼容与回滚**：导入前自动备份；导入失败不改任何文件（先写临时目录再原子替换）。
`data.db` 的 schema 只向前迁移：旧包 → 新机可以由 `store.migrate()` 升级；新包 → 旧机拒绝。

**代码落点与工作量**

- 新包 `internal/profile`：打包/解包、manifest 校验、字段白名单、背景图迁移、备份与原子替换（约 400 行 + 测试）；
- `internal/settings`：导出/导入用的「可移植字段」白名单与合并（约 80 行）；
- `internal/view/page_settings.go`：两个按钮 + 预览/确认弹窗（约 120 行）；
- `internal/cli` + `main.go`：两个参数与启动顺序（约 80 行）；
- 文档与测试（roundtrip、跨平台路径改写、schema 拒绝、旧设置缺字段）。

### 1.4 D 方案（同步文件夹）——已按反馈移除

**2026-11-04 更新：用户实测后认为「同步文件夹」不好用，已整体移除**（`settings.SyncFolder`、
设置页区块、`profile.List`/`Bundle`、相关测试与文档均已删除）。

保留的判断仍然成立：**不建议「两台机器同时写同一个 sqlite」**——云盘并发写同一文件会损坏/互相覆盖；
同步粒度只能是「整包文件 + 人工确认」。如果以后重做目录/云盘同步，应先把这一条写进 UI 提示。

### 1.5 C 方案（自建服务）为什么先不做

需要：账号体系、设备配对、鉴权、存储与配额、版本与回滚、冲突合并、HTTPS、备份、隐私合规、
服务端监控与升级。对「三台自己的电脑」这个场景，收益（自动同步）不抵成本；
如果将来要多用户/团队，再考虑，或直接支持 WebDAV（Nextcloud）而不用自建存储。

## 二、伴生桌宠

### 2.1 技术可行性（对照 mygo 能力）

mygo 已具备做桌宠需要的窗口能力：

| 能力 | mygo API | 用途 |
|---|---|---|
| 无边框窗口 | `WindowOptions.Frameless` | 只显示宠物本身 |
| 透明背景 | `WindowOptions.Transparent` | 桌面透出 |
| 置顶 | `WindowOptions.AlwaysOnTop` / `SetAlwaysOnTop` | 浮在其他窗口上 |
| 不占任务栏 | `WindowOptions.SkipTaskbar` / `Panel` | 不污染任务栏 |
| 拖拽移动 | `Element.DragWindow()` | 拖宠物 |
| 双击 | `Element.DoubleClicked()` | 双击唤回主窗口 |
| 点击穿透（可选） | `Window.SetIgnoreMouseEvents` | 「不挡鼠标」模式 |
| 多窗口 | `mygo.NewWindow` + `Parent` | 跟随主窗口生命周期 |

结论：**可行，不需要框架改动**。

### 2.2 交互与 MVP（建议定下来的范围）

**第一版（MVP）**

1. 设置 → 常规 →「桌宠」：开关、皮肤（简笔猫 / 简笔狗）、大小（小/中，实际就是 3 档缩放）、
   「回到屏幕中央」、「不挡鼠标」模式。
2. 显示：无边框透明置顶小窗（初始 160×160，可拖拽，位置记忆，跨屏校正到可见区域）。
3. 交互：单击有反应（眨眼/跳一下）；双击唤回主窗口；右键菜单（打开主窗口 / 隐藏桌宠 / 设置）。
4. 成长：按**前台使用时长**累积经验，4 个阶段（幼崽 0–2h、少年 2–10h、成熟 10–30h、成年 30h+），
   体型上限约 1.5 倍；阶段与经验持久化；升级时一个小动画 + 轻提示。
5. 久坐提醒：默认 45 分钟，可设 20–120 分钟；到点气泡 + 系统通知（复用 `notifyTaskDone` 的通道），
   点气泡可「休息一下 / 稍后提醒」。
6. 待办速记：点宠物 → 小气泡输入框 → 回车保存；主窗口「功能演示 → 待办清单」可查看/勾选。
7. 任务状态：主窗口跑轻量/重量任务时，宠物显示「忙碌」状态（案头小动画），完成后撒小花。

**刻意不做（v1）**：好感度/喂食/换装商店/语音/联网/多宠物/桌宠间互动。
这些都是「养成游戏」成本，和「低占用伴生工具」的定位冲突。

### 2.3 成本评估（目标：不占 CPU/GPU）

| 项 | 设计 | 量级 |
|---|---|---|
| 空闲绘制 | 静止时不请求帧，只保留一张静态画 | 0 fps、0% CPU |
| 待机动画（呼吸/眨眼） | 8–12fps，只在窗口可见时；尊重系统「减弱动态效果」 | 约 3–5% 单核（120Hz 屏幕上也一样，因为限帧） |
| 交互动画 | 点击/升级时短暂 12fps | 可忽略 |
| 内存 | 小窗 surface 160×160×4 ≈ 100KB + 矢量形状缓存 | <2 MB |
| 磁盘 | 无图片资源，纯矢量绘制 | <10 KB 状态 |
| 主窗口隐藏/托盘 | 桌宠窗口一起隐藏，动画停止 | 0 |
| 启动 | 只在开关打开时创建窗口 | 惰性 |

**结论**：做得克制的话，桌宠对性能的影响远小于一个浏览器标签页；关键约束是
「静止不请求帧、动画限帧、隐藏即停」——这三条会写进实现与测试。

### 2.4 跨平台注意

- **Windows**：透明 + 置顶 + 跳过任务栏都稳定；拖拽用 `DragWindow`。
- **macOS**：透明/置顶可用；但「在所有 Space 上显示」与全屏应用之上，需要额外窗口层级设置，
  mygo 未必暴露；MVP 先接受「当前桌面 + 普通窗口之上」。Dock 图标仍是主应用。
- **Linux**：X11 + 合成器可用；**Wayland 下窗口定位/置顶受协议限制**（客户端不能随意
  设置全局位置），可能只能居中且不能置顶。建议：检测到 Wayland 时在设置里禁用桌宠并说明原因，
  或退化成「主窗口内浮层」。
- **多显示器 / 高 DPI**：记住相对位置（按主屏百分比），恢复时校正到可见区域，防「宠物跑到屏幕外」。

### 2.5 代码结构与可裁剪性

- `internal/pet/`：纯逻辑（经验/阶段/提醒计时/绘制路径），不依赖 App，可单测；
- `internal/view/pet_window.go`：窗口生命周期与输入；
- 设置项：`petEnabled` / `petSkin` / `petScale` / `petReminderMinutes` / `petXP` / `petStage` /
  `petPos`；前四项进 `settings.json`（可跨设备同步），运行态（XP/位置）建议进页面状态或单独小表。
- 「新建项目」生成器：桌宠属于基座功能，建议保留（代码量小，且是产品差异化）；
  若不想带，删 `internal/pet` + `pet_window.go` + 设置区即可（生成器可加一个开关）。

### 2.6 分期与工作量

| 阶段 | 内容 | 预估 |
|---|---|---|
| P1 | 透明置顶窗 + 矢量宠物 + 开关 + 拖拽 + 位置记忆 | ~500 行 + 2 个测试 |
| P2 | 成长/阶段/经验 + 久坐提醒 | ~250 行 |
| P3 | 待办速记 + 任务状态联动 | ~200 行 |
| P4 | 皮肤打磨 / 换装（可选） | 视需求 |

风险：透明置顶窗口在部分 Linux 桌面的观感；「总会挡一点东西」需要「不挡鼠标」与
「仅主窗口活跃时显示」两个开关来平衡。

## 三、多套主题（已实现）

### 3.1 设计：明暗 × 配色，两个维度

- **明暗**（已有）：跟随系统 / 浅色 / 深色 —— 决定背景、描边、正文、滚动条；
- **配色**（新增）：只替换**强调色系**（主按钮、选中项、图标、焦点环、选中文字）。

这样每套配色在两个明暗下都自动成立，不用维护 4×2 份完整主题；默认「跟随系统强调色」
保持原行为（mygo 已从桌面取强调色），用户选了配色才覆盖。

### 3.2 内置配色

| 名称 | 浅色强调色 | 深色强调色 | 感觉 |
|---|---|---|---|
| 跟随系统（默认） | 桌面强调色 | 桌面强调色 | 与系统一致 |
| 琥珀 | `#b45309` | `#f59e0b` | 暖、稳重 |
| 青碧 | `#0f766e` | `#2dd4bf` | 冷静、工具感 |
| 靛蓝 | `#4f46e5` | `#818cf8` | 科技、接近默认蓝但更紫 |
| 石墨 | `#3f3f46` | `#a1a1aa` | 中性、低饱和，久看不累 |

悬停 / 按下 / 选中 / 焦点 / 强调色上的文字全部由强调色推导（深色提亮、浅色压暗；
亮底自动用深色字），规则与 mygo 的 `Theme.follow` 一致。

### 3.3 实现与验证（本轮已完成）

- `settings.Palette`（旧文件缺字段 → 自动回落 `system`）；
- `internal/view/palette.go`：配色定义 + 每帧覆盖（与背景半透明同一层，绝对赋值幂等）；
- 设置 → 常规 → 外观 →「配色」（跟随系统 / 琥珀 / 青碧 / 靛蓝 / 石墨）；
- 测试：每套配色的浅/深强调色、强调色文字可读、幂等、视图与设置名单一致、持久化、设置页可见；
- 截图已重拍（设置页能看到「配色」一行）。

### 3.4 背景色调（已实现）

- 维度：默认 / 暖白 / 护眼绿 / 午夜蓝 / 樱粉 / 雾蓝 / 青瓷 / 薰衣草 / 摩卡，
  与配色正交（可「护眼绿 + 青碧」）；
- 只替换 `Background / Surface / SurfaceHover / SurfacePressed / Border`，不动正文与强调色；
- 实现顺序：`applyTone` → `applyBackdropTheme`（先定基色，再按浮层透明度降 alpha）→ `applyPalette`；
- 设置 → 外观 →「色调」；测试覆盖浅/深两套、正文对比度、幂等、与设置名单一致、持久化。

## 九、方案 E：GitHub / Gitea / Gitee 仓库托管（已实现，仅手动）

用户提出：配置文件能否直接用 GitHub 或其他代码托管平台上传/更新，每人只管理自己的数据。

### 9.1 形态选择

| 形态 | 结论 |
|---|---|
| **私有仓库 + Contents API** | **采用**。三家平台都有「读/写仓库文件」接口，一套代码即可；历史可追溯。 |
| Gist | 不采用：单文件限制、二进制 base64、结构不清。 |
| Release 附件 | 不采用：每次同步产生 release/tag，噪音大。 |
| 第三方网盘 API | 不采用：又一套账号与密钥，与「仓库管理」诉求不符。 |

### 9.2 已实现的 E 方案

- **平台**：GitHub / Gitea / Gitee；设置页分段选择。Gitea 需填实例地址，GitHub/Gitee
  用默认 API（测试时可覆盖）。
- **认证**：个人访问令牌（PAT），只建议授权单个私有仓库的 contents 读写。
  **明文存本机 `settings.json`**，导入/导出配置包时都会剔除（`profile` 的 machineKeys），
  设置页明确提示。
- **仓库约定**：`profiles/<设备名>.mygo-profile.zip`（留空时的默认值，每台机器一个文件，
  避免互相覆盖）；分支默认 `main`，可改。包格式与方案 A 完全一致（manifest 校验、备份、
  背景图迁移都复用）。
- **操作**：设置页只有三个按钮——「测试连接」「上传当前配置」「从仓库下载并导入」。
  **没有自动上传、没有后台轮询**；下载后先校验 manifest，再交给导入流程（本机先备份，
  完成后重启）。
- **实现**：`internal/repo`（Contents API 客户端，约 450 行，含 httptest 测试）、
  `internal/view/repo_io.go`（表单、后台请求、结果提示）；令牌/仓库字段属于本机设置。
- **并发/覆盖**：默认路径按设备名分文件；如果用户把多台机器填成同一路径，后上传的会覆盖
  先前的远端文件（本机导入仍有 `.bak-<时间>` 备份）。
- **已知限制**：Contents API 对大文件（>1MB）的 GET 可能不直接返回 base64，客户端会退回到
  平台给出的下载地址；再大就需要 Git Data API/Release 附件。仓库体积会随每次上传增长，
  需要用户定期清理历史或换用新的仓库。
- **风险**：PAT 泄露（限制 scope、可随时吊销）、网络不可用（以本地包为准）、私有仓库
  仍需平台可用。
