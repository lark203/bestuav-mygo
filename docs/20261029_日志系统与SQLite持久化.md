# 20261029 引入日志系统与 SQLite 持久化

## 一、背景

现状：应用所有业务数据都在内存（`App.tasks`、`lic.history`），关掉就没了；出错时只有
Go 运行时默认的 panic 输出，且不落盘——用户报障时拿不到任何现场信息。

目标两件事：

1. **日志**：系统错误 / 崩溃时能留下可排查的记录，且自带「用户机器信息 + 系统信息」，
   不用再反复追问「什么系统、多少核、装在哪」。
2. **SQLite**：业务数据落地持久化（重启后仍在）。

## 二、选型与取舍

### 2.1 SQLite 驱动：`modernc.org/sqlite`（纯 Go）

| 方案 | 结论 |
| :--- | :--- |
| **modernc.org/sqlite v1.61.0** | **采用**。纯 Go，`CGO_ENABLED=0` 不变，三平台交叉编译与单文件打包不受影响 |
| mattn/go-sqlite3 | 否决。cgo 实现，性能更好，但要 gcc 工具链，会打破项目「纯 Go 无 cgo」这一核心优势 |
| JSON / CSV 落盘 | 否决。无事务、无索引、无 SQL 查询，数据量一上来还得再迁 |

实测代价：二进制 **14.5MB → 22MB**（+7.5MB），进程常驻内存无明显变化。

### 2.2 日志：标准库 `log/slog` + 自写按天轮转

- 不引入 zap/logrus/lumberjack：`slog` 是标准库，JSON handler 够用，轮转逻辑只有约 60 行。
- 按天而不是按大小：桌面应用日志量小，按天更容易对上「用户说昨天出问题」。

### 2.3 什么进库、什么不进

- **进库**：任务记录、授权凭证历史、应用事件（含错误/崩溃）。
- **不进库**：用户偏好仍是 `settings.json`。单机单用户的键值配置用 JSON 是业界惯例
  （electron-store / .NET user.config 同理），搬进数据库只增加迁移成本与故障面。
  这条结论原本就写在 `internal/settings` 的包注释里，本次保持不变。

## 三、实现

### 3.1 新增包

| 包 | 职责 |
| :--- | :--- |
| `internal/apppath` | 路径唯一来源：`ConfigDir()` / `LogDir()` / `DBPath()`（settings 的 configDir 也改为委托它） |
| `internal/logging` | slog JSON + 按天轮转保留 7 天 + `Recover` 崩溃捕获 + `EnvSnapshot` 环境快照 + `Recorder` 入库回调 |
| `internal/store` | SQLite：建表迁移、任务/授权/事件 DAO、计数统计 |
| `internal/view/persist.go` | 界面状态 ↔ 数据库的胶水层（启动恢复、写入双写、空库退化） |

依赖方向（新增部分，无环）：

```
view → store → apppath
view → logging ← (Recorder 回调) ← main 注入 store.RecordEvent
store 不 import logging；logging 不 import store
```

`logging` 与 `store` 之间靠 `logging.SetRecorder(func(level, kind, msg, detail string))`
单向回调连接，参数全是基础类型——避免两个基础设施包互相依赖。

### 3.2 表结构（`<配置目录>/data.db`）

```sql
task(id, name, kind, status, cost, created_at)               -- 异步任务记录
license_record(id, subject, edition, term, token, created_at) -- 授权凭证历史
app_event(id, ts, level, kind, message, detail)              -- 事件/错误/崩溃
schema_meta(key, value)                                      -- schema_version、演示数据标记
```

连接参数：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=1`；
`SetMaxOpenConns(1)` 串行化（桌面单写入者，彻底避免 `SQLITE_BUSY`）。

### 3.3 关键设计点

1. **库是持久化真源，内存切片只是本帧缓存**：启动 `AttachStore` 读库恢复，写入时双写。
2. **首次灌演示数据用标记位，不是「表空就灌」**。否则用户清空任务后，下次启动又冒出来。
3. **库不可用优雅退化**：`a.store == nil` → 全部读写走内存，界面照常。`TestNilStoreDegradesGracefully` 锁定。
4. **崩溃捕获后重新抛出**：`defer logging.Recover("view")` 只负责留下 CRASH 日志与堆栈，
   不改变原有崩溃行为（吞掉 panic 会让界面停在不一致状态，更难查）。
5. **入库规则分两级**：`Event()` 只有 ERROR+ 入库（文件才是全量）；`Audit()` 无条件入库。

### 3.4 踩到的时序缺陷（真实 bug，已修）

第一版把「应用启动」审计写在 `setupLogging()` 里，而事件入库管道是在 `openStore()` 里才
挂载的 → **Audit 发生在管道挂载之前，事件只进了日志文件，库里 `app_event` 为 0**。

实测发现：跑起来后查库 `事件=0`。修法是把启动审计拆成独立的 `announceStartup(dbReady bool)`，
在「日志 + 数据库」都就绪后再调用。修复后重新跑实例，库里出现：

```
事件: 10-29 12:23:24 | INFO | app | 应用启动 |
      build=...·8a7e6c6; os=windows; arch=amd64; go=go1.27.3; cpus=12; store=已启用
```

## 六、遗留与后续

1. **无真正的「系统版本号」**：`runtime.GOOS` 只给 `windows`，拿不到 Windows build 号。
   要补需引入 `golang.org/x/sys/windows`（`RtlGetVersion`）或读注册表，本轮为控制依赖未做。
2. **崩溃只有堆栈，没有 core dump**：Go 在 Windows 上不产 minidump；如需崩溃转储要接
   `MiniDumpWriteDump`，属于后续增强。
3. **事件表暂无导出入口**：数据已入库，但「一键导出诊断包（日志 + 事件 + 环境）」还没做，
   建议作为下一次迭代（界面加一个按钮即可，逻辑全在 store 层）。
4. **日志级别不可配**：当前固定 INFO；若将来日志量变大，可把级别放进 settings.json。
5. **多实例并发写库**：`SetMaxOpenConns(1)` 只解决单进程内串行；开启「允许多开」后多个进程
   会同时写同一个 `data.db`（WAL 允许单写多读，`busy_timeout=5000` 可缓解）。若成为问题，
   应改为「每实例独立库」或「主实例统一写」。
